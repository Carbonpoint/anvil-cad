# Geometry Kernels for a From-Scratch Rust CAD/CAM System

Review date: 2026-09-09. Produced by a Sonnet research agent for the Anvil project.

## 1. Why the kernel is the hard part

Every serious CAD system is built around a geometry kernel: the library that stores solids as boundary representation (B-rep) data, evaluates NURBS curves and surfaces, and runs booleans, fillets, offsets, and healing. Sketching, the parametric feature tree, and the GUI are all comparatively tractable engineering problems. The kernel is where decades of PhD research and commercial engineering effort live, and it is the part that decides whether a "Siemens NX class" tool is realistic. This section surveys the field as it stands in 2025-2026.

## 2. Commercial kernels, for context

**Parasolid** is the kernel inside Siemens NX and Solid Edge, and it is licensed into more than 350 other CAD/CAM/CAE products. It is closed source, owned by Siemens, and licensed through Siemens' Parasolid business and via Tech Soft 3D. It matters here because it defines the bar: decades of engineering on **tolerant modeling**, where every face, edge, and vertex carries a local numerical tolerance so that "gappy" or slightly inconsistent geometry (from imports, numerical error, or user mistakes) can still be booleaned and filleted without the kernel throwing an unrecoverable topological error. Parasolid also added **Convergent Modeling**, which lets B-rep and triangulated facet data live in the same model and be operated on with the same booleans and fillets, useful for AM and reverse engineering. None of this is available as source code; it can only be read about, not copied.

**ACIS**, from Spatial (owned by Dassault Systèmes since 2000), is the other major commercial kernel, historically used by AutoCAD and many mid-market CAD/CAM packages. ACIS and Parasolid together underpin roughly 90% of commercial CAD. It is also closed source, licensed per-seat/per-product. Dassault's newer kernel, CGM (used in CATIA and newer SOLIDWORKS), is likewise proprietary. There is no legal way to base an open-source project on ACIS, Parasolid, or CGM source; they exist here only as a benchmark and a source of published algorithmic ideas.

## 3. Open-source B-rep kernels: the mature C++ option

**OpenCASCADE Technology (OCCT)** is the only open-source kernel genuinely comparable in scope to Parasolid or ACIS. It has full NURBS curve/surface geometry, a real B-rep topology model (vertex/edge/wire/face/shell/solid), general boolean operations (`BOPAlgo`, including the newer General Fuse framework and "fuzzy" tolerance-driven booleans for touching/near-coincident geometry), constant and variable-radius fillets and chamfers (`BRepFilletAPI_MakeFillet`/`MakeChamfer`), shelling, drafting, lofting, sweeping, and shape healing to repair bad imports. It reads and writes STEP (AP203, AP214, AP242), IGES, STL, and more. Its license is LGPL 2.1 with an additional exception (since version 6.7.0, 2013) that permits static linking into closed-source applications without forcing source disclosure, so it is commercially usable, unlike a plain GPL/LGPL library. As of September 2026 the OCCT GitHub repository has nearly 2,900 stars, over 670 forks, and commits within the last few days, so it is actively maintained (by Open CASCADE SAS in France, which also sells commercial support). The honest caveat: OCCT's boolean and fillet code is famous for edge cases. Its issue tracker and forum have recurring reports of `MakeFillet`/`MakeChamfer` crashing or hanging on specific topologies (missing edges after intersection, non-90-degree wall angles, B-splines not supported in 2D fillets), and its API is old-style C++ with a steep learning curve. It is robust in the sense of "handles most real models most of the time with careful tolerance tuning," not in the sense of "provably correct."

**CGAL** (Computational Geometry Algorithms Library) is a different kind of tool: an academic-grade library of exact geometric algorithms, not a CAD-shaped modeler. Its 3D Nef Polyhedra package gives boolean operations (union, intersection, difference, complement) that are closed and exact, including non-manifold and unbounded cases, but Nef polyhedra are a polyhedral (planar-faced) representation, not curved NURBS B-rep, so it is not a drop-in CAD kernel. Its licensing also complicates use in a permissive project: base "Kernel" and support packages are LGPL, but most higher-level algorithms, including Nef polyhedra, are GPL with a commercial dual-license sold by GeometryFactory. A project wanting to ship closed or permissively-licensed binaries cannot casually depend on CGAL's boolean code.

**Manifold** (elalish/manifold) takes a different angle: guaranteed-manifold triangle-mesh booleans, Apache-2.0 licensed, written in C++ with Python/JS/C bindings, and heavily parallelized. It is very active (over 2,200 GitHub stars, commits within days as of September 2026) and has been adopted as an alternative backend in OpenSCAD (no longer experimental since the 2024.09 release) and by BRL-CAD to make its `facetize` command more robust. Manifold's guarantee is real and its performance is excellent, but it operates on triangulated meshes, not analytic NURBS surfaces, so fillets, exact cylinders, and STEP-quality curved geometry are out of scope; it is a strong complement to a B-rep kernel (tessellated preview, 3D-print export, a facet fallback path) rather than a replacement for one.

**SolveSpace** is smaller in scope: an open-source (GPL) parametric sketcher with a genuinely good 2D/3D constraint solver, plus a basic B-rep layer supporting STEP import/export and simple booleans (union, difference, intersection) between extrude/revolve/lathe/helix groups; its own docs note real ordering limitations on chained booleans. Its value here is less the modeling kernel and more the constraint-solving architecture, a well-tested reference design for a sketch solver.

**BRL-CAD**, the US Army's decades-old open-source CAD system, is worth a mention as the other successful strategy: it never adopted mainstream B-rep booleans at its core. It keeps a CSG representation and evaluates booleans by ray-tracing/spatial classification rather than by intersecting boundary surfaces, sidestepping much of the topological-repair problem that plagues B-rep booleans, at the cost of not being the feature-history B-rep modeler NX users expect.

## 4. Pure-Rust efforts: promising but immature

**truck** (ricosjp/truck) is the most serious pure-Rust attempt. It is genuinely B-rep: `truck-geometry` implements B-spline/NURBS curves and surfaces, `truck-topology` implements vertex/edge/wire/face/shell/solid, `truck-modeling` combines them for extrude/revolve-style construction, `truck-shapeops` provides boolean operations on solids, `truck-meshalgo`/`truck-polymesh` handle tessellation, and `truck-stepio` reads and writes STEP files (built on the companion `ruststep`/`espr` crates). It renders through wgpu, so it is GPU-agnostic and works headless on CPU too. License is Apache-2.0, friendly for a permissive project. As of September 2026 it is meaningfully active: about 1,550 GitHub stars, over 2,800 commits, and a push within the last two days. That said, it has no fillet/chamfer operation at all, its booleans are less battle-tested than OCCT's, and its STEP I/O is a thinner layer than OCCT's deeply tested translator. It is a toolkit for building a kernel, not yet a kernel matching OCCT's coverage.

**Fornjot** (hannobraun/fornjot) was the other high-profile pure-Rust B-rep kernel and is directly relevant as a cautionary tale: after years of sponsored development it was shut down in 2025/2026 by its own author, who wrote candidly that he had promised a path to something meaningfully better than existing tools and never got there, and felt he could not keep taking sponsorship money without believing in that path. The repo (2,555 stars) is now archived. The lesson is not "Rust CAD kernels are impossible," it is that a from-scratch kernel is a multi-year, research-grade undertaking that can consume a small team without reaching feature parity, even with real community interest and funding.

**opencascade-rs** (bschwind/opencascade-rs) sidesteps the "write a kernel" problem entirely: a Rust binding to OCCT built with `cxx.rs`, vendoring OCCT as a git submodule and exposing higher-level, more ergonomic wrappers over a lower-level `opencascade-sys` layer. It is LGPL-2.1 (inherited from OCCT), actively developed (pushed within the last two weeks as of September 2026, 262 stars, 72 forks), but its own docs call the high-level API "still in flux." A second, independent project (`occt-rs/occt-rs`) links dynamically against a system-installed OCCT via pkg-config instead of vendoring it. Both prove that FFI to OCCT from Rust is workable engineering today.

**cavalier_contours** (jbuckmccready) is narrower still: a pure-Rust, Apache-2.0, no-unsafe 2D polyline library for offsetting, combining, and boolean operations on lines and circular arcs, actively maintained. It is the right scope for 2D sketch-profile offsetting inside a sketcher, not a 3D kernel, but a good example of a small, correctly-scoped Rust geometry crate a larger project could depend on directly.

**KittyCAD/Zoo** is worth naming even though it is not open in the relevant sense: Zoo (formerly KittyCAD) built its own GPU-oriented geometry engine from scratch and exposes it only as a hosted API with a Rust client; the modeling app is open source but the engine is not. It is not a candidate dependency, only evidence that a well-funded team building a from-scratch kernel in 2024-2026 chose to keep the kernel closed and monetize it as a service.

## 5. How robust booleans and fillets actually get built

Two separate hard problems hide inside "robust booleans": numerical robustness (avoiding wrong answers from floating-point round-off in intersection tests) and topological robustness (producing a valid, closed, manifold-where-expected B-rep even when inputs are nearly degenerate: coincident faces, near-tangent surfaces, gaps smaller than working precision).

Numerical robustness is largely a solved academic problem. Jonathan Shewchuk's 1996-97 paper "Adaptive Precision Floating-Point Arithmetic and Fast Robust Geometric Predicates" gives exact, adaptive-precision orientation and incircle predicates that run nearly as fast as plain double-precision arithmetic but never give a wrong sign. These predicates sit under most modern computational-geometry codes, including CGAL and mesh-boolean tools; a small Rust crate, `georust/robust`, ports exactly these predicates for Rust projects (Delaunay triangulation, point-in-polygon, mesh booleans). A from-scratch Rust kernel should build its low-level geometric tests on exact predicates like these from day one rather than trusting raw `f64` comparisons.

Topological robustness for curved B-rep is the part that is still genuinely hard, and is mostly "engineering plus decades of bug reports" rather than a clean algorithm. The classic reference is Ian Stroud's book "Boundary Representation Modelling Techniques" (Springer, 2006), the closest thing to a textbook on how real B-rep kernels structure data and implement Euler operators, non-manifold topology, and the plumbing that keeps a solid valid through edits. Parasolid's and ACIS's approach, and the one OCCT also uses, is **tolerant modeling**: every topological entity carries a tolerance value (not a single global epsilon), and two entities are coincident whenever the distance between their underlying exact geometry is within the sum of their tolerances; booleans and fillets then reason in terms of these tolerance zones instead of assuming exact coincidence. OCCT's "fuzzy" boolean option expresses this directly: an extra fuzz value lets the algorithm merge near-coincident faces and edges that would otherwise make the intersection code produce garbage. On the meshed side, corefinement approaches such as "Simple and Robust Boolean Operations for Triangulated Surfaces" and Manifold's guaranteed-manifold algorithm show the analogous, more tractable story for triangle meshes: a real correctness guarantee is achievable once curved analytic surfaces are given up.

Fillets and blends add their own difficulty on top of booleans. The classical formulation is the "rolling ball": the fillet surface is swept by a ball of the fillet radius rolling along the edge, tangent to both adjacent faces; its center traces a spine curve, the offset-surface intersection curve of the two faces offset inward by the radius. This is why fillets are implemented as marching/continuation algorithms over the spine rather than one closed-form surface, why variable-radius fillets need a nonlinear solve for the spine, and why fillets interact badly with nearby geometry (short edges, vertices where several filleted edges meet, nearly tangent adjacent faces), requiring many special-cased corner constructions. This is exactly the category of bug OCCT's issue tracker is full of, and exactly the feature that took Parasolid and ACIS many person-years to make reliable.

## 6. STEP support in Rust

STEP (ISO 10303) is non-negotiable for interoperability with NX, SolidWorks, CATIA, and manufacturing tooling; AP203 (basic solid geometry and assembly structure) and AP214 (adds color, layers, and GD&T) are both formally withdrawn/superseded but still the most commonly produced files in the wild, while AP242 (2014-) is the converged, actively maintained protocol adding semantic PMI, kinematics, and better long-term-archival features, and is what new tools should target for export.

In Rust, the state of the art is the **ruststep**/**espr** pair from ricosjp: `espr` compiles ISO 10303-11 EXPRESS schema definitions into Rust types and parsing/serialization code, and `ruststep` is the runtime that reads/writes the STEP ASCII exchange format (Part 21) against those generated types, aimed at replacing the aging C `stepcode` project. It ships generated bindings for AP201 and AP203; AP214/AP242 schema coverage is not yet a finished, turnkey feature. `truck-stepio` builds on this to get STEP geometry into truck's B-rep types. As of September 2026, ruststep's GitHub activity has gone quiet (last push in March 2025), so treat it as usable-but-slow-moving infrastructure. There is also a smaller, independent `iso-10303` crate (J-F-Liu) for parsing STEP structurally. No Rust project currently has anything close to OCCT's mature `STEPControl`/`STEPCAFControl` translators, which handle AP203/214/242 with PMI, assembly structure, and years of interoperability fixes against real files from every major CAD vendor. For the foreseeable future, "good STEP support" in a Rust CAD tool realistically means either FFI to OCCT's STEP translator or a sustained investment in ruststep/espr to reach AP242 coverage and vendor-file compatibility.

## 7. Recommendation: what is actually realistic

**(a) Writing an entirely new kernel from scratch in Rust** is the option to be most honest about. Fornjot is direct, recent proof that this is a multi-year research undertaking even for a motivated, funded, focused developer, and it did not reach a usable kernel. Numerical robustness (exact predicates) is tractable and has good Rust building blocks already (`georust/robust`). Topological robustness for curved B-rep booleans and general fillets is less a solved problem in the literature than an accumulated body of institutional engineering knowledge inside Siemens and Dassault; replicating even OCCT's level of coverage, itself considered less robust than Parasolid by most practitioners, took large teams a very long time. Choosing this path makes the application's schedule a geometry-kernel research project's schedule.

**(b) Building on truck** is more realistic but still means co-developing the kernel, not just consuming it. Truck gives a reasonable, Apache-2.0, actively-maintained NURBS/B-rep/boolean foundation with STEP I/O and no C++ toolchain dependency, valuable for a "pure Rust, easy cross-platform build" goal. But it currently lacks fillets entirely, and its booleans/STEP layer have had far less real-world testing than OCCT's; this path means writing and contributing upstream a fillet/blend engine and a lot of robustness hardening, essentially a slice of option (a)'s hard work, but starting from useful primitives instead of nothing.

**(c) FFI to OCCT** (via `opencascade-rs`, `occt-rs`, or a project's own `cxx`/`bindgen` layer) is the pragmatic, fastest path to NX-like capability today: full NURBS, mature general booleans with fuzzy-tolerance handling, constant/variable fillets and chamfers, STEP AP203/214/242 import-export, and shape healing, all CPU-only and cross-platform since OCCT itself builds on Linux, Windows, and macOS. The cost is real: OCCT's API is old-style C++, its fillet/boolean code still has known edge-case failures a project would inherit rather than control, its LGPL-with-exception license must be tracked correctly for distribution, and "written from scratch in Rust" becomes untrue at the kernel layer, which matters if the goal includes memory-safety or supply-chain claims.

**(d) A hybrid strategy** is the honest recommendation. Use OCCT via FFI as the load-bearing kernel from day one, since it is the only open-source option with genuinely NX-comparable booleans, fillets, NURBS, and STEP AP242 coverage, and let the team spend its time on what differentiates a new tool: the parametric feature-history model, the sketch constraint solver (SolveSpace's solver is a good reference, plus truck/cavalier_contours-style 2D geometry for the sketch plane), the GUI, and CAM. In parallel, invest incrementally in Rust-native geometry (contribute fillets and hardening to truck, grow ruststep/espr's AP242 coverage, or adopt Manifold/cavalier_contours for mesh-preview and 2D-offset paths where a mesh-level or 2D guarantee is enough) so an OCCT-independent path becomes possible later, without betting the first working release on that maturation happening on schedule.
